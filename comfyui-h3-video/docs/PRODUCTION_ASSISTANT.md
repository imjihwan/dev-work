# Grok 영상 제작 도우미

일반·갤러리·이어 만들기 화면에 대화형 제작 도우미가 붙는다. 넓은 PC 화면(1280px 이상)은 오른쪽 채팅 패널이 기본으로 열리고 작업 영역이 그 옆에 배치된다. 작은 화면에서는 오른쪽 아래 **제작 도우미 · Grok**을 눌러 넓은 채팅 화면으로 연다. 기존 2번의 프롬프트 작성 도우미는 그대로 사용할 수 있다. 공식 Grok CLI 계정 로그인은 공유하지만, 제작 도우미는 웹 조작과 앱 API 조회·실행까지 연결한다.

## 대화형 화면

질문과 답변은 말풍선으로 쌓이며, 변경안·변경 전후·실행 버튼은 해당 답변 바로 아래 카드에 표시한다. 실행 후에는 같은 카드에 전달/중단 상태가 남는다. 이어 질문하면 이전 제안은 읽기 전용으로 보관하고 최신 변경안만 실행할 수 있다.

PC의 **넓게**는 채팅 전체 화면, **분할 보기**는 작업 화면 옆 채팅으로 전환한다. **접기**로 대화를 유지한 채 작업 화면에 돌아간다. 열림/접힘·응답 방식·작성 중인 입력은 브라우저별로 저장한다. 최근 대화는 서버에 저장해 PC·휴대폰·아이패드와 LAN/Tailscale의 다른 주소에서도 같은 세션을 본다. 열린 화면은 약 2초 간격과 다시 활성화될 때 갱신한다.

입력칸은 긴 글에 맞춰 높이가 늘어난다. PC에서는 Enter로 보내고 Shift+Enter로 줄바꿈한다. 터치 기기에서는 Enter로 줄바꿈하고 보내기 버튼을 사용한다. Ctrl/Command+Enter도 지원하며 한국어 조합 중 Enter는 전송하지 않는다. 응답 중에도 다음 요청을 작성할 수 있고, 전송 실패 시 작성 문구를 복원하되 이미 작성 중인 새 문구는 덮어쓰지 않는다.

이전 대화를 읽고 있으면 새 답변이 와도 스크롤을 강제로 내리지 않는다. **최신 대화로**를 눌러 이동할 수 있다. **새 대화**는 모든 기기의 서버 대화를 지우며 누른 기기의 채팅 초안도 비운다. 다른 기기의 미전송 초안과 앱의 입력·대기열은 유지한다. 채팅 입력 이벤트는 편집 화면과 이어 만들기 프로젝트의 입력 변경으로 처리하지 않는다.

## 사용

- `현재 최종 프롬프트와 설정을 설명해줘`
- `대기 2번 프롬프트를 가져와 현재 내용과 비교해줘`
- `대기 2번의 해당 문구만 바꿔줘. 나머지는 유지해줘`
- `길이를 5초로 바꾸고 현재 사진으로 1순위 대기열에 추가해줘`
- `실행 중인 건 유지하고 대기 3번만 취소해줘`
- `현재 작업을 같은 설정으로 다시 시작해줘`
- `저장된 설정 묶음의 이름을 바꿔줘`
- `갤러리에서 지정한 항목을 즐겨찾기에 넣어줘`

기본은 변경안 확인 후 **변경안 실행**이다. **명확하게 요청한 변경은 바로 실행**을 켜면, 모델이 직접 실행 요청으로 판정하고 코드의 명령문 검사도 통과한 경우 자동으로 실행한다. 이 선택은 브라우저·접속 주소별로 유지한다. 질문·설명·제안은 자동 실행하지 않는다. 기존 화면이 제공하는 확인 창·유효성 검사·파일 선택 절차는 유지한다.

대화는 최근 12개 메시지와 최신 미적용 변경안을 참고한다. 입력값이나 사진 선택이 바뀌면 기존 변경안의 실행을 중단하고 다시 요청하도록 안내한다. **새 대화**는 도우미의 맥락과 변경안을 지우며 입력·대기열·결과를 삭제하지 않는다. 도우미 요청 취소와 영상 작업 취소는 별개다.

## 접근 범위

현재 화면의 입력값, 자동·수동 **최종 프롬프트**, 선택 목록, 버튼, 체크 상태, 앱의 상태 메시지를 전달한다. 일반 화면과 이미 로드된 같은 출처의 갤러리·이어 만들기 iframe을 함께 다룬다. 탭이 현재 선택되어 있지 않아도 입력값을 조작할 수 있으며, 아직 로드되지 않은 화면은 앱 API를 사용한다. 비밀번호와 파일 선택 경로는 제외한다. 파일 선택은 사용자가 직접 해야 한다.

대기열은 처음에는 순서·ID·상태·진행률만 전달한다. **대기 N번은 ComfyUI의 실제 대기 순서**를 뜻하며 완료 이력의 최근순과 다르다. 필요한 항목만 `queue_item`으로 조회해 ComfyUI에 들어가 있는 실제 최종 프롬프트와 기록된 입력·설정을 가져온다. 다른 항목도 요청에 필요한 경우 조회할 수 있다. 이력·갤러리·저장 설정·모델 카드·이어 만들기 프로젝트는 등록된 JSON API로 조회한다.

앱 API의 생성·우선추가·대기 수정·취소·재시작·설정 묶음·모델 조합·카드 설정·갤러리·편 생성/확정/병합·폴더 열기 기능을 호출할 수 있다. 현재 화면의 조작은 실제 입력 이벤트와 기존 버튼 동작을 사용한다. 사진·영상 표시·다운로드·파일 선택은 기존 웹 화면의 기능으로 요청하며, 미디어를 모델이 직접 시각적으로 분석하는 기능은 아니다.

사진·영상 바이트는 Grok에 전송하지 않는다. 저장 설정·프로젝트 API가 반환한 미디어 배열·경로·data URI도 전달 전에 제거한다. 현재 사진으로 생성하거나 사진이 포함된 설정 묶음을 저장할 때는 **브라우저가 기존 로컬 앱 API에만** 사진을 전달한다. Grok의 `"$current_settings"`·`"$current_generation"` 등의 이름을 브라우저에서 실행 직전에 실제 값으로 해석한다.

## 실행 방식

1. 브라우저가 입력·선택·버튼을 임시 참조 번호로 요약한다. 현재 최종 문구는 기존 자동 재조립 규칙으로 최신화한다.
2. Grok은 필요한 JSON 조회를 먼저 요청한다. 호스트가 허용된 앱 조회만 수행하고 결과를 다시 전달한다.
3. Grok은 설명과 변경안을 JSON으로 반환한다. 임의 셀렉터·스크립트·외부 URL·셸 명령은 실행하지 않는다.
4. 호스트가 실제 컨트롤, 정확한 원문, 선택 목록, 변경 대상과 현재 상태를 검사한다. 공통 항목의 이름을 매번 다시 말해야 하는 키워드 검사는 하지 않는다. 요청 범위와 이전 대화·미적용 수정안을 Grok이 함께 해석한다. 편집 범위와 재작성 정도는 요청 맥락에 따라 판단하며 특정 공통 항목을 기본 보호하는 별도 지침은 두지 않는다. 최종 문구 직접 수정과 원본 텍스트 칸 수정은 한 변경안에서 섞지 않는다.
5. 실행 시 변경안·단계별로 한 번만 승인 기록을 잡는다. 중복 클릭·통신 결과 불명은 자동 재실행하지 않는다. 여러 단계 중 일부가 처리됐을 수 있으면 현재 앱 상태를 확인하도록 알린다.

대기 항목의 문구는 부분 교체와 전체 재작성이 모두 가능하다. 일괄 요청은 한 건의 일괄 API 작업으로 처리하며 개별 항목 수정 계획을 나열하지 않는다. 공통 문구 변경은 `patch-queue`의 `all_pending:true` 또는 `ids`와 `edits`를 사용한다. 공유 설정·최종 프롬프트 적용은 기존 `queue/bulk-edit`를 사용한다. 조회 시 문구 해시를 기억하고, 적용 직전 문구와 전체 실행 그래프가 바뀌지 않았는지 검사한다. 수정할 노드는 기존 Director뿐이다. 표시용 `prompt`뿐 아니라 DaSiWa가 실제 사용하는 `builder_state.simple_prompt`, 타임라인의 구성 정보·해석된 프롬프트·이어 만들기 프롬프트도 함께 맞춘다. 다른 설정·사진·순서·노드 연결은 유지한다. 변경된 최종 문구는 이력의 수동 최종 문구에도 함께 저장된다.

입력칸 전체 재작성은 `replace` 동작으로 새 문구만 받는다. 호스트가 현재 원문을 붙여 기존 `set` 동작으로 검증·실행하므로 긴 원문을 모델이 다시 복사할 필요가 없다. 실행 전 원문 불일치나 최종/원본 칸 혼용은 한 번 수정 계획을 다시 받되 실제 쓰기는 재시도하지 않는다. 통합 동작 모드에서는 `actionText`만, 시간별 모드에서는 `shot-N-action`만 노출해 숨겨진 중복 입력에 의한 덮어쓰기를 막는다.

현재 화면을 수정한 다음 전체에 적용할 때는 `patch-queue`의 `{all_pending:true,prompt:"$current_prompt"}`를 사용한다. 브라우저가 앞선 입력 수정 후 최신 최종 문구를 바인딩하므로 같은 대화에서 반복 적용해도 처음 문구를 재사용하지 않는다. 기존 `edits` 부분 교체도 모든 구성 정보에 동일하게 적용한다. 이 API는 사진·시드·설정·대기 순서를 보존하고 실행 중인 항목을 제외한다.

이전 버전에서 이미 저장된 수정과 구성 정보가 어긋난 경우, 운영자용 `POST /api/production-assistant/repair-prompt-state`로 검사할 수 있다. 기본 `dry_run:true`이며 `false`일 때만 복구한다. 이력에 수정 시각이 있고 이력·화면 최종 문구·대기열 표시 문구가 모두 같은 항목만 대상이다. 다른 구성 정보와 실행 중인 작업은 보존하며 응답은 검사·대상·복구·실패 건수만 반환한다. 자동 시작 복구나 임의 프롬프트 변경은 하지 않는다.

도우미 전용 대기 취소는 해당 ID만 제거하며, 조회 뒤 대기→실행으로 넘어간 항목을 임의로 중지하지 않는다. 현재 작업 중지·재시작은 조회한 실행 ID를 사용한다. 기존 웹의 `전체 중지`와 같은 기능은 앱 API로 대상 목록을 명확히 전달한다.

## 한계와 개인정보

- 이는 웹앱 전용 연결이다. Grok CLI의 파일·셸·웹 검색·스킬·MCP 도구는 계속 비활성화한다. 웹 기능의 PC 폴더 열기 외에 임의 파일 탐색이나 OS 명령을 제공하지 않는다.
- 큰 목록은 페이지 단위로 조회한다. 한 요청은 조회 단계 최대 5회, 한 조회 단계 4건, 변경 동작 8개로 제한한다. 대상이 많으면 범위를 나눠 요청한다.
- 브라우저의 파일 선택·자동 재생·클립보드 제한 등으로 사용자의 추가 조작이 필요할 수 있다. 버튼을 눌렀다는 응답은 영상 생성 완료를 뜻하지 않는다. 앱의 실제 진행 상태를 확인해야 한다.
- 모델은 자연어를 오해할 수 있다. 기본 확인 모드에서 변경 대상·내용을 먼저 검토할 수 있다.
- 전달한 입력·조회 문구와 대화의 외부 처리·기록은 Grok 계정/CLI 설정을 따른다. 전용 계정 폴더는 Git에서 제외한다. 자동 실행 설정·미전송 초안은 브라우저에, 공통 대화 표시 기록은 서버의 비공개 `production-chat.json`에 저장한다. 기록은 최근 최대 100개 메시지(문구/변경 전후 표시와 작성 중인 입력)로 제한하며, 저장 용량이 부족하면 오래된 기록부터 줄이고 저장 실패를 화면에 알린다. API 실행에 쓰는 변경안·claim 기록은 UI 서버 메모리에만 둔다(15분 만료). 브라우저 기록에 실행 ID·DOM 대상·입력 스냅샷·사진 바인딩은 저장하지 않는다. 복원한 변경안은 읽기 전용이며 새로고침 전 진행 중이던 요청을 자동 재전송하거나 재실행하지 않는다. 이전 실행의 완료 여부는 앱 상태로 확인하고 필요하면 새 변경안을 요청한다.

## 검증

실제 사용자 작업·사진·결과물을 조회하거나 실제 작업을 제출하지 않았다. 가상 화면·대기열·프롬프트를 사용해 계획 검증, 조회 후 수정, 읽기/쓰기 분리, 정확한 부분 교체, 오래된 대상 거절, 중복 실행 방지, 로컬 사진 바인딩, 확인/자동 모드, 최종 문구 접근을 검사한다. 실제 Grok CLI 시험에서도 합성 문구와 모의 앱 API만 사용한다. 브라우저를 열거나 실제 미디어를 재생하는 검증은 하지 않는다.

## 응답 속도와 품질 선택

헤더는 **Grok 4.7**을 표시하며 정밀/최대/균형/빠르게를 고를 수 있다. 기본은 정밀(high)이며 고정 조건·정확한 문자열 교체·실행 보호를 유지한다. 최대(xhigh)는 더 오래 걸릴 수 있다. 추론 강도 선택은 브라우저에 저장한다. 처리 중에는 준비·Grok 응답·앱 정보 조회·검사 단계, 호출 차수와 경과 시간을 표시한다. 상태 확인 간격은 0.6초다.

최초 대기열은 20개만 보여 주며 `total`, `has_more`, 실행·대기 개수를 함께 전달한다. 생략된 항목도 `queue`의 offset/limit(최대 100) 또는 `queue_item`의 원래 순번으로 접근할 수 있다. 원래 전체 스냅샷은 로컬 검증용으로 보관하며 항목 순서·문구·설정은 바꾸지 않는다. 같은 요청 안의 동일 조회는 재사용하고 동일 결과를 중복 누적하지 않는다. 다른 요청에는 캐시를 공유하지 않는다. 현재 폼에 이미 있는 값은 재조회하지 않고 독립 조회는 묶어서 요청하도록 지시한다.

모델에 전달하는 폼에서는 반복 false 플래그만 생략하고 모든 입력 문자열은 그대로 둔다. 답변과 변경안은 최종 JSON 검증이 끝난 뒤 표시한다. 네트워크·계정 부하·필요 조회 횟수에 따른 지연은 남으며 고정 배수의 속도 향상을 보장하지 않는다.

## 응답 속도와 품질 선택

헤더에 실제 모델인 **Grok 4.7**을 표시한다. 기본은 **정밀(high)**이며 **최대(xhigh)·균형(medium)·빠르게(low)**를 같은 모델에서 선택한다. 선택은 이 브라우저의 접속 주소별로 기억하며 요청 중에는 변경하지 않는다. 품질을 우선하면 정밀 또는 최대를 사용하고, 빠르게는 추론 시간을 줄이는 선택으로 제공한다. 입력 문구의 길이나 고정 조건은 줄이지 않는다.

대기 중 준비·앱 정보 조회·Grok 응답·변경안 검사 단계, 응답 차수와 경과 시간을 보여준다. 완료 확인 간격은 0.6초다. 모델 진행 이벤트도 실시간으로 표시하되 실행 버튼은 전체 JSON과 원문 검증을 통과한 뒤 표시한다.

전체 대기열 스냅샷은 로컬 검증에 유지하되 모델에는 처음 20개 메타데이터만 보낸다. `queue`의 offset/limit로 추가 페이지를 보고 `queue_item`의 원래 대기 번호로 직접 뒤쪽 항목도 조회한다. 한 요청 안에서 동일한 조회 결과를 재사용하고 중복 결과를 다시 누적하지 않는다. 다음 요청에는 새 스냅샷과 새 조회를 사용한다.

## 기기 간 공통 대화

서비스 갱신 후 기존 대화를 남기고 싶은 브라우저에서 먼저 새로고침한다. 서버가 비어 있을 때 그 브라우저의 기존 기록을 한 번만 가져온다. 다른 기기의 별도 옛 대화를 자동으로 합치거나 이미 있는 서버 대화를 덮어쓰지 않는다. 이전 로컬 기록은 전환 전 백업으로 남고, 공통 새 대화를 불러온 기기에서는 지운다.

서버가 사용자 메시지·Grok 답변·변경안 표시·실행 전달 결과를 직접 기록하므로 요청 후 브라우저를 닫아도 완료한 답변을 다른 기기에서 볼 수 있다. 동시에 쓰거나 오래된 화면에서 새 대화를 지우면 revision 비교로 덮어쓰기를 거절한다. 읽기 전용으로 불러온 제안에는 실행 권한이나 DOM 대상을 복원하지 않으며 새 대화/다른 기기의 후속 요청 이후 이전 미실행 제안은 서버에서도 거절한다.

서버 재시작 전 처리 중이던 요청은 상태 확인 안내로 남기고 자동 재실행하지 않는다. 저장 파일의 깨짐·디스크 오류는 기록을 비우는 대신 오류로 알린다. 저장은 임시 파일과 원자적 교체로 처리하고 작업 내용·사진 바이트·인증 토큰·실행 그래프를 별도로 수집하지 않는다. 이 파일은 Git에서 제외한다. 이 서비스에 접근 가능한 기기는 공통 대화를 볼 수 있다.

공통 대화는 화면이 보일 때 약 2초 간격으로 갱신한다. revision과 세션이 같으면 메시지 본문을 다시 내려받지 않는다. 화면으로 돌아왔을 때도 갱신한다.

## 새 답변 표시

새 답변을 확인하지 않았으면 접힌 제작 도우미 버튼과 상단 모델 배지에 빨간 점을 표시한다. 공유 대화에서 다른 기기의 답변이 도착했을 때도 적용한다. 대화를 열거나 마지막 답변을 읽으면 지우며, 읽음 표시는 브라우저별 메시지 ID만 저장한다. 대화 원문을 알림 저장소에 복사하지 않는다. 백그라운드 브라우저가 일시정지된 경우 화면으로 돌아오면 동기화한다.

## 긴 응답 대기

빠르게/균형/정밀/최대에 따라 호출 제한 180/300/600/900초를 적용한다. 조회 왕복을 포함한 전체 요청은 900초 예산으로 제한한다. 대기 화면은 현재 호출의 실제 제한을 표시한다. 취소는 유지하며 시간이 초과돼도 앱에서 자동 재전송하거나 다른 모델·API로 전환하지 않는다. 타임아웃 진단은 원문 없는 숫자 정보만 기록한다.

## 요청 중 새로고침

진행 중인 공유 요청이 있으면 새 요청을 보내지 않고 기존 요청의 처리 단계·응답 차수·전체 경과 시간을 이어 표시한다. 기기 소유자를 추측해 무조건 다른 기기의 요청이라고 표시하지 않는다. 새로고침 뒤에도 알려진 현재 도우미 요청 ID로 응답 중지를 할 수 있고 영상 생성은 중지하지 않는다. 완료·오류·취소 기록이 도착하면 대기 문구와 잠금을 해제한다. 이전 변경안은 계속 읽기 전용이다.

## 실시간 처리 단계

요청 중 Grok 연결 준비 → 응답 대기 → 추론 중 → 답변 작성 → 응답 형식 확인과 앱 정보 조회·변경안 검사 단계를 실제 이벤트에 맞춰 표시한다. 모델 신호는 약 1초 간격으로 갱신하며 시작 기기는 약 0.6초, 다른 기기·새로고침한 화면은 약 2초 간격으로 상태를 확인한다. 진행 신호 횟수와 마지막 수신 시간도 표시한다. 이는 내부 사고 원문이나 생성 완료율이 아니다. 이벤트가 없으면 추론 중이라고 만들어 표시하지 않는다.

공유 진행 메타데이터는 메모리에만 두고 매 신호마다 대화 파일이나 revision을 갱신하지 않는다. 같은 revision의 메시지 생략 응답에도 최신 진행 상태를 포함한다. 다음 호출·완료 시 이전 신호를 지우며, 늦게 도착한 이전 요청의 신호는 무시한다. 답변·변경안은 전체 검증을 끝낸 뒤 기존 방식으로 표시한다.

## 대화 맥락에 따른 작업

항목명 키워드가 최신 한 문장에 없다는 이유로 공통 조건 수정을 막던 검사를 제거했다. 최근 사용자 대화와 당시 수정안을 바탕으로 짧은 승인·추가 수정·조언 요청을 해석한다. 최신 취소·정정·범위가 우선하며 입력값·API 결과에 들어 있는 문구는 새로운 지시로 취급하지 않는다. 사소한 선택은 알아서 판단하고 앱에서 확인할 수 있는 정보는 먼저 조회하며 결과/대상을 크게 바꾸는 정보가 부족할 때만 질문하도록 한다.

자동 실행 옵션은 유지한다. 특정 명령어·문장부호·승인 표현을 검사하지 않고 Grok이 대화 맥락에서 판단한 실행 의도를 사용한다. 조언·설명은 계속 자동 실행하지 않는다. 원문 일치·컨트롤 유효성·실행 직전 상태·중복 실행 방지와 미디어/OS 접근 범위는 유지한다. 이전 수정안은 후속 요청 시 실행 권한을 잃지만 당시 표시된 내용은 새 계획을 만드는 맥락으로 제공한다.

폐기한 ‘공통 조건은 해당 항목의 변경을 명확히 요청한 경우에만 수정합니다.’ 오류는 모델에 넘기는 대화/현재 상태에서만 제외한다. 기존 표시 기록을 지우지 않으며 새 대화를 시작할 필요는 없다.

설명 답변에 수정안이 함께 있으면 검토 가능한 제안으로 표시한다. 설명을 실행 의도로 간주하거나 자동 실행하지 않는다.

## 편집 재량과 일괄 처리

문구를 글자 단위로 보존하거나 얼굴/카메라/원테이크 항목을 기본 보호하라는 별도 지침을 제거했다. 실제 사용자가 명시한 제한은 따르며 도우미가 목적에 맞춰 문구 전체를 재작성하거나 설정을 조정할 수 있다. 원문 정확 일치 검사는 실행 사이 내용이 바뀌었는지 확인하는 기술 검사로만 남는다. 전체 현재 값을 before로 지정하면 전체 재작성이 가능하다.

자동 실행 후보는 Grok의 intent=execute 판단을 사용하며 ‘가능/왜/어떻게’ 같은 단어 때문에 막지 않는다. 실제 실행은 기존 브라우저의 확인/자동 선택을 따른다. 설명·제안은 자동 실행하지 않는다.

`patch-queue`는 기존 단일 id 외에 ids 또는 all_pending:true를 받는다. 전체 범위는 최초 페이지 20개나 조회한 예제에 한정되지 않는다. 하나의 API 작업에서 해당 범위 전체의 공통 문구를 교체하고 대상/수정/확인 수 및 실패를 반환한다. 실행 중·다른 소유자의 항목은 제외하고 각 항목의 그래프와 순서/사진/설정은 기존 검사로 보존한다. 일치하지 않는 문구는 해당 항목 실패로 보고하며 전체 성공이라고 간주하지 않는다.

## 화면 표시와 조작 대상

활성화된 쓰기 가능한 입력은 접힌 영역·모바일 비표시 영역·비활성 탭에 있어도 input/change 이벤트로 수정한다. 이미 로드된 비활성 iframe도 수집하며 억지로 새 탭을 로드하거나 미디어를 열지는 않는다. 버튼은 실제 클릭 전에 해당 앱 탭·모바일 만들기/이력 화면·details를 필요한 경우 자동으로 연다. 임의의 숨김·비활성 상태를 무조건 해제하지 않는다.

고유 DOM id를 사용한 조작안은 현재 ref로 연결한다. 없는 대상·비활성/읽기전용 항목·열 수 없는 버튼은 실행 전에 이유를 구분하고 Grok에 피드백해 다른 API/대상을 최대 한 번 다시 계획한다. 검증 실패 계획은 실행하지 않았으므로 이 단계에서 작업이 중복 적용되지는 않는다. 전체 900초/최대 5회 예산 안에서만 수행하며 공급자 오류·타임아웃·실행 결과 불명은 재전송하지 않는다.

이전 ‘현재 화면에서 사용할 수 없는 대상입니다.’ 오류는 저장 표시 기록을 지우지 않고 모델 맥락에서 제외한다. 이후에도 실제로 사라지거나 비활성화된 대상은 조작하지 않으며 해결되지 않으면 구분된 원인을 알린다.
