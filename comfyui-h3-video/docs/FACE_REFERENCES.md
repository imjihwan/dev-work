# 여러 사진으로 얼굴 일관성 보강하기

## 확인한 동작

H3 Ref2VA는 이미지 참조를 최대 9장 받는다. 공식 프롬프트 가이드는 같은 대상을 여러 자료에서 참조할 때 하나의 `<Subject N>`으로 묶고 각 자료의 역할을 명시하도록 안내한다. 사진 9장을 별도 인물이나 순서대로 재현할 포즈로 설명하지 않는 것이 이 화면의 목적이다.

이 화면의 서버는 사진 배열을 같은 순서의 Director slot/order로 전달한다. Director는 사진 참조를 순서대로 수집하고 H3 노드는 각 참조를 텍스트 인코더와 연결된 video VAE 경로에 전달한다. 합성 입력 9장으로 제출 순서와 첫 사진 고정 연결을 검사했다. 실제 개인 사진이나 생성 결과를 검사한 것은 아니다.

H3 참조 처리 코드 자체는 얼굴을 자동으로 검출·분리하지 않고 이미지 전체를 축소해 사용한다. 그래서 이 화면은 **얼굴인식강화** 옵션(기본 꺼짐)을 켰을 때 사진 2~9를 CPU 얼굴 검출(YuNet)로 얼굴 주변만 잘라 보조 참조로 넣는다(일반 추가·순차 추가 모두, 아래 '자동 크롭'). 그 밖의 경우 ‘얼굴 보조’는 프롬프트로 지정한 역할이다. 검출 모델이나 OpenCV 가 없으면 등록을 막지 않고 원본 사진으로 진행하며, 화면에 그 이유를 표시한다(`/api/health` 의 `face_detector_ready` 로 준비 여부 확인). 배경과 옷이 많은 전신 사진보다는 얼굴이 충분히 크게 나온 보조 사진이 얼굴 정보를 더 잘 전달할 수 있다는 판단이며, 이 화면에서 품질 향상 수치를 측정한 것은 아니다.

소스 템플릿의 기본 `ref_image_size`는 `match`다. 각 사진을 비율을 유지하며 생성 영상의 픽셀 면적에 맞춰 축소한다. `max`는 더 높은 참조 해상도를 허용하지만 참조 정보가 매 샘플링 단계에서 사용되므로 시간·메모리 부담이 커질 수 있다. 이번 변경에서는 참조 해상도·모델·LoRA·스텝을 바꾸지 않았다.

첫 장면 고정은 첫 프레임 위치에 넣는 가이드다. 영상 전체에서 얼굴의 모든 픽셀이나 표정이 고정되는 기능은 아니므로, 이후 표정·가림·움직임 중에도 정체성이 유지되도록 별도의 참조 설명이 필요하다.

## 사진 구성

- 사진 1: 얼굴, 머리, 체형, 옷·악세사리, 장면의 기준 사진.
- 사진 2~9: 같은 인물의 선명한 얼굴 보조 사진. 정면과 완만한 좌우 측면 등 실제로 다른 정보를 제공하는 사진을 고른다.
- 얼굴 형태가 달라 보일 정도의 보정, 큰 나이 차이, 심한 가림·흔들림·극단적인 광각 사진은 참조 간 충돌 가능성을 늘릴 수 있다. 서로 일관된 사진으로 비교하는 것을 권한다.
- 얼굴 보조 사진의 표정이나 고개 방향은 영상에서 따라 할 동작이 아니다. 기본 얼굴 방향과 상·하체 동작은 사진 1 및 기존 장면 지시가 담당한다.

9장을 모두 쓸 수 있지만 장수가 늘수록 품질이 단조롭게 좋아진다는 보장은 없다. 같은 조건에서 적은 장수와 9장을 비교하되 사진 1·시드·모델·LoRA·장면을 유지하면 차이를 판단하기 쉽다. 모델·LoRA 변경이나 과격한 얼굴 동작을 함께 바꾸면 사진 효과를 구분하기 어렵다.

여러 사진을 하나의 영상에 함께 참조하려면 **기본 대기열 추가**를 사용한다. 사진 개별 추가는 사진당 별도 작업이며, 사진 순차 추가는 기준 사진을 회전한다. 기준 얼굴·의상·구도를 유지하려는 비교에는 일반 추가가 적합하다.

## 이번 코드 보완

1. 여러 파일을 병렬로 읽은 완료 순서가 사진 번호를 결정하던 부분을 수정했다. 이제 브라우저가 전달한 선택 순서대로 하나씩 읽으며 남은 참조 슬롯까지만 읽는다. 첫 사진 읽기에 실패하면 다음 사진을 조용히 기준으로 승격하지 않는다.
2. 인물 설명에 `<Picture 1>`이 이미 있어도 사진 2~9의 얼굴 역할이 빠지지 않도록 자동 조립을 수정했다. 실제 등록 장수의 사진 번호를 모두 쓰고 하나의 인물로 연결한다.
3. 보조 사진이 새로운 표정·고개 회전·카메라 이동·장면 전환을 요청하지 않도록 명시했다. 표정·말하기·눈 깜박임 중 얼굴 비율과 자연스러운 비대칭을 유지하도록 보강한다. 기존 카메라·상체·하체 지시는 보존한다.
4. 직접 편집하거나 이력에서 복원한 최종 프롬프트는 자동으로 덮어쓰지 않는다. `현재 사진 참조 문구만 반영`을 누르면 얼굴 참조 문단만 추가·갱신한다. 다른 문장·장면 시각·직접 편집 상태는 유지한다. 이 기능이 넣은 문구는 반복해서 눌러도 중복되지 않으며 사진 수가 줄면 해당 문구의 사진 번호도 갱신한다.

수정은 앞으로 화면에서 조립하거나 사용자가 명시적으로 갱신한 프롬프트에 적용된다. 이미 대기 중이거나 실행 중인 작업을 자동으로 수정하지 않는다. 사진을 보고 인물을 검증하거나 결과 영상을 분석하는 기능을 추가하지 않았다.

## 순차 대기열의 보조 사진 자동 크롭 검토 (2026-11-16)

원본 9장에 대해 얼굴 주변 크롭 9장을 한 번씩 준비한 뒤, 각 순차 작업에는 해당 원본을 Picture 1로, 나머지 사진의 크롭 8장을 Picture 2~9로 넣는다. 기준 사진의 전체 구도·옷·악세사리를 보존하면서 얼굴 보조의 배경·몸 비중을 줄인다. 구현은 `simple_ui/face_references.py`와 서버의 순차 조합 경로에 있다. 여러 얼굴은 박스 면적이 가장 큰 얼굴을 고른다. 원본은 기존 ComfyUI 입력 파일을 쓰며 별도 영구 인물 저장소는 만들지 않는다.

연구용 CPU 프로토타입은 `logs/face-crop-research/probe.py`에 있으며 결과는 같은 폴더의 `report.json`이다. 공개 scikit-image astronaut 사진 한 장에서 해상도·밝기·평면 기울기를 바꾼 9개 입력만 사용했다. 서로 다른 9장, 실제 측면 얼굴, 가림, 다양한 인종·연령에 대한 검출 성능을 검증한 것은 아니다. 원본의 크기를 키운 시험 입력은 새로운 얼굴 디테일을 만들어내지 않는다.

- OpenCV YuNet으로 단일 얼굴 검출 9/9. 얼굴 박스의 긴 변 약 2배를 포함하는 여유 있는 정사각형 크롭. 눈·코·입 랜드마크가 범위 안에 남는지 확인.
- 모델 로딩·다운로드를 제외한 9개 검출·크롭 처리 약 0.16초(이 PC, 1 CPU 스레드). 실제 사진 크기·디코딩·전송까지 포함한 서비스 지연 시간은 아니다.
- 9개 순환 조합 모두 Picture 1은 해당 원본, Picture 2~9는 순서에 맞는 나머지 크롭임을 검사. 원본 배열의 픽셀은 변경되지 않음.
- 가장자리 좌표 조합 48개에서 잘못된 범위·얼굴 랜드마크 잘림이 없는지 검사.
- 얼굴이 없는 입력과 얼굴이 둘인 입력은 자동 선택하지 않고 원본 유지 대상으로 분류.
- 640×640 출력 면적의 `match` 계산에서 큰 시험 입력의 얼굴 픽셀 폭은 약 1.6~2.3배. 작은 512px 입력은 약 1배이며 32px 단위 정렬 때문에 약간 줄기도 함. 이는 참조 처리 크기의 차이이며 생성 얼굴 유사도·정확도 점수가 아니다.

설계 시 필요한 조건:

1. 기존 순차 추가와 별도 선택 옵션을 제공하고, 원본은 항상 보관한다. 각 원본의 크롭을 미리 한 번 계산해 재사용한다. 작업마다 8장을 새로 검출할 필요가 없다.
2. EXIF 방향을 먼저 정규화하고 비율을 유지한다. 작은 얼굴을 인위적으로 확대하거나 얼굴 복원 모델로 생김새를 재작성하지 않는다. 얼굴 박스는 머리 전체·모자 전체의 분할 결과가 아니므로 여백만으로 항상 모두 포함된다고 보장할 수 없다.
3. 사용자의 최종 지정에 따라 여러 얼굴은 면적이 가장 큰 얼굴을 선택한다. 낮은 신뢰도·지나치게 작은 얼굴·크롭 범위 불량은 원본으로 유지하고 장수를 표시한다. 같은 인물인지 확인하는 얼굴 인식과 얼굴 위치 검출은 다른 기능이다. 구현은 위치 검출만 한다. 위 연구용 초기 프로토타입의 여러 얼굴 원본 유지 정책은 실제 구현에서 변경됐다.
4. 이미지 목록을 단순히 크롭 배열로 교체한 뒤 회전하면 Picture 1까지 크롭되는 문제가 생긴다. 작업별로 `원본[k] + 나머지 크롭의 순환 순서`를 따로 구성하고, 앵커·자동 캔버스·갤러리 기준 썸네일은 원본[k]를 사용한다. 이력·재생성에는 실제 제출한 참조 조합을 보존해야 한다.
5. 크롭을 강제로 확대하지 않으면 `match`의 참조 면적은 대체로 같거나 줄어든다(32px 반올림 예외). 단, 이를 실제 생성 속도나 메모리 감소의 측정 결과로 해석하지 않는다.

검증 결론: 순차 처리 구조와 크롭 전처리는 구현 가능하고 큰 입력의 얼굴 픽셀 손실을 줄이는 근거가 있다. DaSiWa GXS Turbo 생성 결과가 실제로 더 닮는지는 아직 검증하지 않았다. 최종 확인에는 같은 사진 1·프롬프트·시드·모델·LoRA·길이·화질로 **원본 보조 8장 / 크롭 보조 8장**만 바꾼 비교가 필요하다. 실제 생성이나 개인 작업 열람은 이번 조사에 포함하지 않았다.

## 사진 수와 크롭 크기의 생성 시간 실측 (2026-11-24)

위 5번에서 미뤄 둔 생성 속도를 측정 전용 ComfyUI 에서 합성 인물로 쟀다(조건·표는 [PERFORMANCE](PERFORMANCE.md)의 '참조 사진 수와 보조 사진 크기').

- 사진 1 + 얼굴 크롭 8장은 사진 1장보다 한 편이 거의 두 배 걸린다(5초 768×960: 168초 → 324초). `match` 는 사진마다 생성 화소 수까지만 줄이므로, 생성 화소 수보다 큰 크롭 여덟 장은 각각 영상 한 프레임 크기의 참조가 된다.
- 크롭의 긴 변을 640·512 로 줄이면 251초·222초가 된다. 합성 인물에서는 동일 인물 점수가 내려가지 않았다(말하기 0.815 → 0.84~0.85, 움직임 0.69 → 0.71, 장면당 한 시드). 다만 그 크롭은 768×960 생성 프레임을 키운 것이라 줄여도 잃을 세부가 거의 없었고(키우지 않은 1152 크롭으로 다시 재도 평균 점수는 같았지만 그것도 생성 영상의 프레임이다), 크롭 안의 얼굴은 긴 변 640 에서 약 320화소, 512 에서 약 256화소가 된다(크롭은 얼굴 긴 변의 2배). 실제 사진의 닮음은 확인하지 못했다.
- 보조 사진이 어떻게 찍혔느냐가 영상의 구도를 끈다. 같은 여러 장용 문구로 넓게 잡힌 사진 8장을 넣으면 화면 속 얼굴 면적이 0.04 로 사진 1장(0.05)보다 작아지고, 얼굴 크롭 8장을 넣으면 0.10 이 된다. 얼굴 유지 문단(`FACE_REFERENCE_RETENTION`)도 1.2~1.3배 당기며, 인물이 카메라를 보고 말하는 프레임을 늘린다.
- 얼굴 크롭 수에 따른 변화: 인물이 일어나 걸어가는 장면에서 화면 속 얼굴 면적이 사진 1장 0.05 → 얼굴 크롭 2장 0.08 → 4장 0.09 → 8장 0.10 이 됐다(8장은 두 시드). 위 '이번 코드 보완' 3번의 문구("새로운 카메라 이동·장면 전환을 요청하지 않는다")가 있어도 그랬고, 구도 유지 문장을 더해도 달라지지 않았다. 문구는 바꾸지 않고 옵션 설명에 알린다.
- 기본 동작은 그대로다(크롭을 줄이지 않는다). 화면 서버 환경 변수 `SIMPLEUI_FACE_CROP_MAX` 로 얼굴 크롭의 긴 변 상한을 줄 수 있다(`crop_reference()` — 256 미만은 256, 크롭이 상한보다 작으면 그대로, 키우지 않는다). 사진 1 과 원본 그대로 넣는 보조 사진에는 적용하지 않는다.

## 근거와 검증 범위

### DaSiWa v5 GXS Turbo 추가 조사 (2026-11-16)

대상은 DaSiWa v5 GXS Turbo다. 일반 H3 비터보 모델의 20~25스텝 권장값을 이 체크포인트의 권장값으로 옮기지 않는다. 작성자 모델 카드의 해당 버전은 조사 도구에서 열리지 않아 세부 권장값을 재확인하지 못했다. 고정된 작성자 C-MMH3-33 공개 워크플로의 안내에는 Turbo 4~8스텝이 적혀 있다. 따라서 8스텝은 이 범위 안에서 비교할 후보이며 얼굴 보존이 반드시 개선된다는 보장은 아니다.

원본 워크플로와 설치된 소스의 경로를 확인했다: Director → Director Guide → `MiniMaxH3ReferenceToVideo`. 이 화면의 공개 템플릿에서 Guide의 CLIP·VAE 연결은 모두 존재한다. Director가 사진 전체를 전처리하고, 기본 노드가 다시 `ref_image_size`에 따라 줄인 뒤 텍스트 인코더 입력과 VAE 참조 잠재값을 만든다. 원본 Director도 `match`다. `input_scaling=Off`만으로는 뒤쪽 `match` 축소가 없어지지 않는다.

**얼굴 보조 크롭을 먼저 비교한다.** 사진 1은 전체 기준으로 유지하고, 보조 사진은 얼굴 전체·이마·턱·귀 주변에 약간의 여백을 남겨 준비한다. 눈·코·입만 아주 작게 잘라 쓰거나 얼굴을 비율이 달라지게 늘리지 않는다. 같은 사진에서 자른 얼굴도 원본보다 새로운 각도 정보를 주지는 않지만, 축소 시 얼굴에 배정되는 픽셀을 늘릴 수 있다. 같은 인물의 실제 다른 각도 사진은 별도의 정보도 제공한다. 이는 처리 코드에 근거한 제안이며 실제 품질 검증 결과는 아니다.

계산 예시(개인 사진 미사용): 2048×2048 사진에서 얼굴 폭이 200px이고 출력 면적이 640×640이면 `match` 축소 뒤 얼굴 폭은 약 62px다. 얼굴 폭 420px인 768×768 보조 크롭은 같은 조건에서 약 350px다. 원본 파일의 총 해상도와 모델이 받는 얼굴 해상도는 다르다. 생성된 영상 속 얼굴 자체가 작다면 참조를 크게 하더라도 출력의 얼굴 세부 표현에는 한계가 있다.

**`max`는 비교 옵션이다.** 기본 구현은 작은 이미지를 확대하지 않는다. 입력이 두 제한보다 이미 작으면 `match`와 `max`가 같은 크기로 처리될 수 있다. 반대로 큰 사진 여러 장을 `max`로 넣으면 매 단계 참조 토큰이 크게 늘어난다. 첫 실험은 보조 사진을 적당한 크기(예: 긴 변 약 1024px로 미리 줄인 입력)로 준비해 비용을 제한하고 비교하는 편이 낫다. 1024px는 이번 조사에서 제안하는 실험 크기이며 DaSiWa 공식 최적값은 아니다. 공개 커스텀 워크플로 작성자들의 `match`/`max` 결과도 엇갈려 `max`가 항상 더 닮는다고 단정할 수 없다.

**추가 LoRA는 분리해서 비교한다.** ComfyUI 공식 가이드도 스타일 LoRA와 참조 사이의 경쟁을 설명한다. 우선 추가 외형·스타일·동작 LoRA가 없는 기준을 만들고 하나씩 되돌려 얼굴 변화와 동작 이득을 구분한다. GXS Turbo 체크포인트 자체에 포함된 효과를 추가 LoRA를 끄는 것으로 제거할 수는 없다. 가중치나 스텝을 한꺼번에 바꾸지 않는다. 일반 모델용 수치나 다른 터보 LoRA를 무조건 덧붙이지 않는다.

**RefMod와 RefCap은 얼굴 학습의 대체물이 아니다.** DaSiWa의 RefMod는 저장된 참조 잠재값과 설명을 재사용하는 기능이며, 작성자 문서는 정체성 분리를 보장하지 않는다고 밝힌다. upstream RefMod의 압축 모드는 잠재값 축소·MSE 보정이며 DiT나 얼굴 인식 손실을 사용한 인물 학습이 아니다. RefCap Replay는 작성자의 검사에서 원래 사진을 넣는 기본 경로와 같은 conditioning을 재현하는 것을 목표로 한다. 이는 참조 보관·재사용의 장점이지 원본 참조보다 더 정확한 얼굴을 자동으로 만드는 증거가 아니다. 해당 프로젝트의 비교도 인원·장면·해상도가 제한돼 DaSiWa GXS Turbo에 일반화할 수 없다.

권장 비교 순서(사용자가 직접 결과 확인, 자동 실행하지 않음):

| 순서 | 바꾸는 항목 | 유지할 항목 / 확인할 점 |
| --- | --- | --- |
| 기준 | 사진 1과 같은 인물 보조 1~2장으로 구성 | 시드·사진 1·동작·길이·모델·앵커를 고정 |
| 1 | 보조 사진만 여백 있는 얼굴 크롭으로 교체 | 같은 보조 원본을 써서 크롭 효과만 비교 |
| 2 | 제한된 크기의 동일 입력으로 `match`와 `max` 비교 | 나머지 동일. 얼굴 일치와 소요 시간 모두 확인 |
| 3 | Turbo 범위에서 4·6·8스텝 비교 | 샘플러·시프트·해상도는 그대로. 매번 한 항목만 변경 |
| 4 | 추가 LoRA를 끈 기준과 하나씩 켠 결과 비교 | 같은 강도·조합을 명시해 외형 변화 요인 분리 |

한 시드에서만 좋아질 수 있으므로 유망한 조건만 추가 시드에서 재확인한다. 얼굴 원형과 움직임 중 일관성을 나눠 평가한다. 초반부터 다르면 참조 해석·크기·모델/LoRA 편향을, 초반은 닮고 후반에 달라지면 표정·회전·가림·시간 흐름의 영향을 우선 의심할 수 있다. 이것은 원인을 확정하는 진단 규칙이 아니라 비교 방향이다.

이번 추가 조사는 코드·공개 워크플로·문헌 및 크기 계산만 사용했다. 현재 개인 작업 설정이나 실제 미디어는 열람하지 않았고, 생성 설정·대기열·실행 중인 작업도 변경하지 않았다.
