사용자 요청: 응답을 빠르게 하되 실제 작업·결과물을 확인하지 말 것. 이후 품질 좋은 모델을 써 달라는 요구가 추가됐다.

변경 범위:

1. 모델은 Grok 4.7 그대로, 기본 **정밀(high)**. **최대(xhigh)·균형(medium)·빠르게(low)**를 선택할 수 있게 한다.
2. 초기 대기열 전달을 상태 메타데이터 20개로 제한하고 전체 수와 다음 페이지 여부를 제공한다. 원본 전체 스냅샷은 호스트가 보관하므로 대상 확인·순서·동시 변경 보호는 유지한다.
3. 추가 목록은 페이지별, 특정 항목은 번호/ID로 조회한다. 사진·실행 그래프를 모델에 넘기지 않는다.
4. 한 요청 안의 동일 조회 결과를 재사용하고 중복 결과를 누적하지 않는다. 다른 사용자 요청 사이에는 캐시를 공유하지 않는다.
5. 프롬프트 문자열은 자르거나 다시 쓰지 않는다. JSON 직렬화 공백과 반복되는 false UI 플래그만 줄인다.
6. 대기 중 준비·조회·Grok 응답·변경안 검사 단계와 경과 시간을 표시하고, 응답 확인 간격을 1.3초에서 0.6초로 줄인다.

구조 개선 후 별도 합성 요청은 정밀(high) 8.42초, 빠르게(low) 4.74초였고 모두 길이 하나만 정확히 수정했다. 입력 직렬화 비교는 23,180자에서 12,194자로 약 47% 줄었다. 횟수가 적고 서버 상태가 변하므로 처리 시간 차이를 일반화하지 않는다. 기본 정밀 모드를 유지한다.

## 고정 180초 타임아웃 수정

긴 응답을 모드와 무관하게 180초에 종료하던 정책을 변경했다. low/medium/high/xhigh의 호출 예산은 180/300/600/900초이며 조회 또는 작성·검토 전체는 900초 예산을 적용한다. 현재 요청의 숫자 시간·제한은 상태 응답으로 제공한다. `local-prompt-helper/grok-timings.jsonl`은 원문·세션/작업 ID 없이 시간·종료 분류·토큰 개수만 저장한다. 진단 파일은 Git에 넣지 않는다. 이는 모든 지연의 원인을 확정하거나 Grok 서버 속도를 높였다는 뜻은 아니다.

UI 재시작 준비는 공유 도우미의 active 플래그를 확인하며 진행 중인 요청이 있으면 프로세스를 멈추지 않는다. 상태 플래그만 점검하고 대화 원문을 출력하지 않는다. 타임아웃 수정은 Python 97개 회귀 검증과 가짜 UI·실제 합성 인사 요청으로 검증했다.

## 실시간 Grok 단계 표시

CLI는 `--include-partial-messages`를 사용해 종료 전 이벤트를 읽는다. 외부 상태에는 `cli_stage` 허용 열거값과 `cli_elapsed_s`·`cli_limit_s`·`cli_signals`·`cli_idle_s` 숫자만 제공한다. 내부 추론/미완성 응답은 보관하거나 UI에 보내지 않는다. 공유 대화의 live_progress는 메모리 전용이며 메시지 revision과 분리한다. UI는 기존 폴링으로 추론/답변 단계·진행 신호 수·마지막 수신 시간을 표시한다. 모델/추론 강도/실행 검증은 바꾸지 않았다. 가짜 이벤트·자식 프로세스·공유 대화·가상 DOM으로 검증한다.

실시간 진행 배포 검증: Python 102개 테스트와 가상 DOM 검증 통과. 작업 정보 없는 실제 CLI 합성 요청에서 시작·대기·추론·답변·응답 형식 확인 다섯 상태와 진행 신호 9회를 3.5초 내 수신했다. 4개 실행 소스와 제공 JS 해시·상태 확인을 마쳤고 간단 화면만 재시작했다. 영상 생성 서버 프로세스는 유지했다. 실제 대화·작업·미디어를 조회하지 않았다.

## 공통 조건 오류 반복 수정

production_assistant.py의 최신 메시지 항목명 정규식으로 공통 수정 자체를 거절하던 검사를 제거했다. SYSTEM은 사용자 대화/제안/후속 승인을 함께 해석하며 최신 정정·범위를 우선하도록 정리했다. 모호하지 않은 일상적 선택과 앱 조회는 도우미가 판단하고, 중요한 정보가 부족할 때만 질문한다. 기존 모델·추론 모드·확인/자동 설정·원문/상태/중복 실행 검증은 유지했다.

production_chat.begin은 기존 변경안 상태를 후속 요청 맥락에 담은 뒤 이전 실행 권한을 무효화한다. LEGACY_COMMON_ERROR는 모델용 대화와 상태에서만 제외하고 기존 표시 기록은 삭제하지 않는다. 코드 검증/스모크는 합성 폼·블록 문구만 사용한다. 실제 대화·작업·사진·결과물을 조회하지 않는다.

대화형 보완 검증: Python 50개 회귀 테스트와 가상 DOM 검증을 통과했다. 실제 Grok의 합성 ‘응’ 승인에서 요청한 한 구간만 수정하는 계획을 6.6초에 받았고, 조언 요청은 9.2초에 실행 없는 설명으로 완료했다. 실제 앱 쓰기는 0건이다. 설명 응답에 수정안이 포함되어도 오류로 막는 대신 확인 가능한 제안으로 표시하고 자동 실행하지 않는다.

## 보수적 편집 지침 제거 및 일괄 처리

글자 단위 편집 보존·공통 항목 기본 보호 지침과 explicit_command/execution_requested 정규식 판별을 제거했다. 자동 실행 후보는 모델의 intent=execute를 사용하며 브라우저의 확인/자동 선택은 유지한다. 기존 원문/대상/그래프/중복 실행 검사는 남는다. 사용자가 실제로 명시한 제한은 따른다.

개별 queue_item 조회/부분 교체 우선 지시를 제거했다. 일괄 요청은 queue/bulk-edit 또는 patch-queue(all_pending/ids)의 한 API 작업으로 계획한다. server.py의 patch-queue 일괄 분기는 전체 대기/지정 범위를 기존 단일 교체 검사로 처리하고 대상별 결과와 실패를 반환한다. 실행 중·외부 소유 작업은 제외하며 순서·사진·다른 그래프 입력을 변경하지 않는다.

합성 검증: 도우미 54개 + 기존 일괄 28개 Python 테스트와 가상 DOM 통과. 실제 Grok에 가짜 대기열 37개 요청을 보내 7.3초에 단일 전체 범위 작업을 받았다(개별 조회 0, 실제 앱 쓰기 0). 실제 작업·대화·미디어는 조회하지 않았다.

## 화면 표시 상태로 인한 대상 오류 수정

production_assistant.js는 활성 쓰기 가능 입력의 수정에 표시 여부를 요구하지 않는다. 로드된 숨김 iframe도 수집하고 버튼 클릭에는 알려진 탭/모바일 뷰/details 경로를 연다. 백엔드는 고유 DOM id를 현재 ref로 연결하며 UnavailableTarget을 원인별로 구분한다. 실행 전 대상 검증 실패에만 한 번 재계획을 허용하고 현재 카탈로그/API로 다른 방법을 찾는다. 실제 쓰기·타임아웃·실행 결과 불명은 재시도하지 않는다. 기존 전체 요청/조회 예산과 실행/그래프 검사는 유지한다.

가상 DOM과 합성 Python 검증을 수행했다. 실제 Grok도 가짜 hidden 입력을 수정하는 한 동작 계획을 5.5초에 반환했다. 실제 앱 쓰기·대화/작업/사진/결과물 조회는 없었다.

배포 확인: 도우미 Python 59개 테스트와 가상 DOM 검증을 통과했다. 실행 소스 3개/제공 JS 해시와 건강 상태를 확인했고 UI 서버만 재시작했다. 영상 생성 서버와 대기열은 유지했다.
