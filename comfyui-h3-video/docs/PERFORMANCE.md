# 성능·장비

## 실측 (원본 PC)

장비: RTX 5060 Ti 16GB, RAM 64GB, Windows 11. 5초 영상, 짧은 변 768(화질 "기본"), 대기 시간 제외.

| 구성 | 스텝 | 걸린 시간 |
|---|---|---|
| DaSiWa v4 터보 int8 (14회) | 4 | 100~186초 (대부분 약 120초) |
| DaSiWa v5 GXS 터보 int8 | 8 | 241초 (스텝당 약 26초) |
| DaSiWa v5 GXS 터보 int8, 768×960, 반복 2개(시드 연속) | 8 | 193초 · 182초 (11/13) |
| 같은 구성·같은 시드, 화질 **초안** 576×736 | 8 | 114초 (11/13) |
| 기본 H3 REF2VA int8 + ref2v 터보 LoRA | 4 | 132초 |
| 기본 H3 FL2VA int8 + fl2v 터보 LoRA, 첫·끝 사진 | 8 | 274초 (모델 교체 불러오기 포함) |

- 반복으로 여러 개 만들면 두 번째부터는 모델이 이미 올라가 있어 조금 빠릅니다(위 193→182초).
- 모델을 바꾼 직후 첫 생성은 불러오기 때문에 더 걸립니다.
- 간단 화면의 "예상 시간"은 `35초 + 스텝 × 26초 × 화질 배수(초안 0.55, 기본 1, 720p 1.6, 1080p 4) × 길이/5초` 로 계산한 **대략값**입니다. 초안 배수는 위 실측((114−35)÷(182−35)≈0.54)으로, 720p·1080p 배수는 실측이 아니라 화소 수로 추정한 값입니다.
- 품질에 영향을 주는 것은 장비가 아니라 **사진 해상도·프롬프트 구체성·시드·스텝**입니다. 같은 설정이면 장비가 달라도 결과 품질은 같고 시간만 다릅니다(압축 형식이 같을 때).

## 생성 시간이 어디에 쓰이나 (실측, 2026-11-23)

`scripts/bench_generation.py` 로 쟀다. 사용자의 ComfyUI 와 분리된 측정 전용 ComfyUI(포트 8198, `logs/bench/` 아래의 별도 입력·출력 폴더)에서 **합성 인물 사진 1장**(모델이 글만으로 만든 가상의 인물)과 합성 문구로 실제 생성했다. 장비: RTX 5060 Ti 16GB, RAM 64GB(측정 중 다른 프로그램이 약 40GB 사용 — 남은 RAM 최소 6~8GB), ComfyUI·노드는 `versions.json` 고정판. 조건: 참조 사진 방식, 768×960, 5초(124프레임), DaSiWa v5 터보 8스텝, euler/simple, shift 7/4.

| 단계 | 시간 | 비고 |
|---|---:|---|
| 샘플링 8스텝 | 약 159초 | 스텝당 19.85초(일정). 전체의 86~91% |
| 영상·소리 디코드 | 13초 | |
| 문구·참조 사진 인코딩 | 6초 | 같은 사진·같은 문구를 다시 돌리면 건너뜀(ComfyUI 캐시) |
| 파일 저장 | 2~4초 | |
| **합계** | **175~185초** | 모델이 이미 올라와 있을 때. 모델을 바꾼 직후 첫 작업은 불러오기만큼 더 걸린다 |

- 속도는 **스텝당 연산**이 좌우한다. 스텝 수·해상도·길이·참조 사진 수(사진마다 토큰이 늘어 모든 스텝이 느려진다)가 곧 시간이다. 문구·사진 인코딩과 저장은 합쳐도 10초가 안 된다.
- GPU 사용률 평균 96~98%, VRAM 최대 15.1GB/16GB. 모델 파일(19.5GB)이 VRAM 보다 커서 일부를 매 스텝 RAM 에서 흘려 넣는다. VRAM 을 쓰는 다른 프로그램(브라우저의 영상 재생 등)을 줄이면 그만큼 빨라질 여지가 있다.

### 쓰지 않는 미리보기 (값만 변경, 적용함)

틀의 미리보기 노드(`2737`, KJNodes)는 스텝마다 영상 전체를 작은 VAE 로 디코드해 노드 위젯용 미리보기를 만들었다. 간단 화면은 이 미리보기를 표시하지 않는다.

| 설정 | 스텝당 | 5초 영상 한 편 | 결과 영상 |
|---|---:|---:|---|
| 원래 값(`tiny_vae: taeh3`, `preview_frames: 120`) | 19.83초 | 175.1초 | 기준 |
| `tiny_vae: none`, `preview_frames: 1` | 19.12초 | 169.0초 | 기준과 프레임 단위로 완전히 같음(PSNR 무한대) |
| 노드를 아예 건너뜀(구조 실험, 적용 안 함) | 19.10초 | 168.9초 | 완전히 같음 |

값 두 개로 노드를 건너뛴 것과 같은 효과가 난다(작업당 약 6초, 3.5%). 미리보기 디코드는 프레임 수·해상도에 비례하므로 긴 영상·큰 화면일수록 절약이 커진다.

### 결과가 같은 속도 노드: 청크 피드포워드 (노드 1개 추가, 적용함)

미리보기를 끈 틀(스텝당 19.12초, 한 편 178.3초)을 기준으로, shift 노드 뒤에 노드 하나를 끼워 같은 시드로 비교했다.

| 구성 | 스텝당 | 5초 영상 한 편 | 결과 영상 |
|---|---:|---:|---|
| 기준(틀 그대로) | 19.12초 | 178.3초 | 기준 |
| **`MiniMaxChunkFeedForward` chunks 4 (지금 기본)** | 17.85초 | 158.8초 | 기준과 프레임 단위로 완전히 같음(2회 측정 모두) |
| chunks 2 | 19.18초 | 169.8초 | 완전히 같음 |
| 어텐션을 `pytorch attention` 으로(값만) | 34.04초 | 296.5초 | 다른 그림(PSNR 29.9dB), 확대 비교에서 화질 차이 안 보임 → 쓰지 않음 |
| `enable_fp16_accumulation` 끔(값만) | 19.13초 | 176.7초 | 완전히 같음 → 이 모델에는 효과 없는 설정 |

- 청크 피드포워드는 계산 순서만 나누는 것이라 결과가 같고, 순간 메모리가 줄어든 만큼 모델 가중치가 VRAM 에 더 머문다. 모델 파일이 VRAM 보다 큰 16GB 이하 카드에서 이득이 난다.
- 틀의 `comfy kitchen attention`(INT8 어텐션)은 정확한 어텐션보다 1.78배 빠르고 눈에 보이는 화질 차이가 없다. 지금 값이 맞다.

### 화면 서버 경로 전체 확인: 세로 사진과 합산 효과

화면 서버 사본을 임시 포트에 띄워 측정 전용 ComfyUI 로 `/api/generate` 를 실제로 불렀다(합성 인물 사진, 같은 문구·같은 시드). 사진은 휴대폰이 세로로 찍은 것처럼 화소를 눕히고 EXIF 방향 6 을 달았다. '동일 인물 점수'는 참조 사진의 얼굴과 영상 16프레임의 얼굴을 얼굴 인식 모델(SFace)로 비교한 코사인 유사도 평균이다(같은 사람은 보통 0.36 이상, 높을수록 닮음).

| 화면 서버 | 모델에 들어간 참조 사진 | 동일 인물 점수(평균 / 최저) | 한 편 | 결과 |
|---|---|---:|---:|---|
| 수정 전 | 960×768 눕힌 화소 + 방향 표시(캔버스는 768×960) | 0.478 / 0.112 | 183.6초 | 머리가 계속 한쪽으로 기울고 사진과 다른 장소 |
| 수정 후 | 768×960 세운 화소 | 0.861 / 0.651 | 167.4초 | 사진과 같은 사람·같은 장소, 바른 자세 |
| 수정 후, 방향 표시 없는 사진 | 768×960 그대로 | 0.854 / 0.640 | 166.7초 | 위와 같은 수준 |

- 방향 표시가 걸린 사진에서는 참조가 사실상 망가진 채 생성되고 있었다. 수정 후에는 방향 표시가 없는 사진과 같은 수준이다.
- 한 편 걸리는 시간은 미리보기 끄기와 청크 피드포워드가 합쳐져 183.6초 → 167초(약 9% 단축)다. 문구·사진 인코딩까지 포함한 화면 서버 경로 전체 기준이다.

### 저장 화질 (값만 변경, 적용함)

같은 시드로 한 번 생성한 뒤 저장 설정만 바꿔 다시 저장했다(샘플링은 캐시되어 각 2초). 기준은 H.264 CRF 0(거의 무손실, 7.53MB). 수치는 휘도 PSNR·SSIM 과 선명도(라플라시안 분산, 기준 28.5).

| 저장 설정 | 코덱 | 5초 파일 | PSNR 평균(최저) | SSIM | 선명도 |
|---|---|---:|---:|---:|---:|
| `quality` 25 (원래 틀) | AV1 | 1.59MB | 45.9 (44.1) | 0.9877 | 21.9 |
| **`quality` 20 (저장 노드 기본값, 지금 틀)** | AV1 | 2.74MB | 47.1 (45.7) | 0.9901 | 24.1 |
| `quality` 16 | AV1 | 3.94MB | 47.7 (46.5) | 0.9911 | 25.5 |
| `quality` 12 | AV1 | 5.87MB | 48.2 (47.1) | 0.9919 | 26.9 |
| H.264 `quality` 18 | H.264 | 3.23MB | 47.2 (45.8) | 0.9903 | 27.0 |
| HEVC 10비트 `quality` 20 | HEVC | 2.05MB | 46.3 (45.0) | 0.9870 | 27.3 |

- 저장 시간은 모두 2~2.6초로 차이가 없다. 눈으로 보면 `quality` 25 는 피부 잔결이 조금 뭉개지고, 20 부터는 기준과 구분하기 어렵다.
- 코덱 `Auto` 는 이 PC 에서 AV1(NVIDIA 하드웨어 인코더, 8비트)을 고른다. 파일은 색 정보 표시(color tag) 없이 기록된다(`ffprobe` 로 확인).
- **색 변환(알려진 작은 오차, 고치지 않음)**: 저장 노드가 남긴 원본 첫 프레임(PNG)과 영상의 첫 프레임을 비교하면, 영상은 BT.601 행렬로 만들어져 있다(BT.601 로 풀면 평균 오차 1.1, BT.709 로 풀면 채도 높은 화소에서 빨강 +3.2·파랑 −2.4 로 치우침, 0~255 기준). 색 표시가 없는 파일을 브라우저가 BT.709 로 가정하면 피부가 아주 조금 붉게 보일 수 있다(프레임 평균 0.7, 화소 95%가 3 이하, 최대 7). 저장 노드에 색 관련 입력이 없어 값으로는 고칠 수 없고, 차이가 작아 결과 파일을 다시 쓰는 후처리는 넣지 않았다.

### 측정 도구 쓰는 법

```powershell
$py = "$env:USERPROFILE\ComfyUI\.venv\Scripts\python.exe"
& $py scripts\bench_generation.py start                 # 측정 전용 ComfyUI 를 8198 에 띄운다(사용자의 8188 이 켜져 있으면 띄우지 않는다)
& $py scripts\bench_generation.py run 계획.json          # 변형을 차례로 생성하고 logs\bench\results.jsonl 에 기록
& $py scripts\bench_generation.py report                # 표로 보기
& $py scripts\bench_generation.py stop
```

계획 파일은 `{"defaults": {...}, "variants": [{"name": "...", ...}]}` 이고, 변형마다 `steps`·`sampler`·`shift_video`·`resolution`·`duration`·`loras` 같은 화면 값과 `overrides`(노드 입력값 바꾸기)를 줄 수 있다. 결과마다 단계별 시간, VRAM 최대·남은 RAM, 영상 지표, 눈으로 볼 프레임 묶음(`logs\bench\sheets\`)이 남는다. `compare`(두 영상의 PSNR·SSIM), `detail`(같은 프레임의 같은 부분을 나란히) 명령으로 변형끼리 비교한다. 측정 중 사용자의 ComfyUI(8188)가 켜지면 하던 작업을 멈추고 측정 인스턴스를 내린다.

## 화면 서버의 조회 부하 (합성 측정, 2026-11-23)

영상을 만드는 속도가 아니라, 화면이 진행 상황을 묻느라 ComfyUI 와 화면 서버에 주는 부하다. 실제 ComfyUI 대신 `scripts/dev_sandbox.py` 의 가짜 ComfyUI(대기 작업마다 실제 템플릿 그래프를 싣는다)와 화면 폴링 흉내로 20초씩 쟀다. 갤러리 진행률 조회 포함.

| 조건 | | ComfyUI 로 간 요청 | 받은 데이터 | 화면 서버 CPU | 가짜 ComfyUI 응답 생성 시간 |
|---|---|---:|---:|---:|---:|
| 대기 20건, 화면 2개(각 20건 추적) | 이전 | 812회 | 73.2MB | 1.20초 | 0.69초 |
| | 이후 | 10회 | 0.03MB | 0.09초 | 0.01초 미만 |
| 대기 300건, 화면 2개 | 이전 | 50회 | 79.9MB | 0.69초 | 0.61초 |
| | 이후 | 10회 | 0.5MB | 0.12초 | 0.01초 |
| 대기 1,000건, 화면 3개 | 이전 | 72회 | 372.9MB | 3.72초 | 3.07초 |
| | 이후 | 10회 | 1.6MB | 0.27초 | 0.02초 |

- 이전: 상태를 물을 때마다 ComfyUI 의 `/queue`(대기 작업의 그래프 전체)를 다시 받았다. 대기 1,000건이면 한 번에 약 8.9MB 다.
- 이후: 표시용 조회는 그래프가 없는 작업 목록(`/api/jobs`)을 1초 동안 나눠 쓰고, 화면은 추적 중인 작업을 한 번의 요청으로 묻는다(화면 서버가 받는 요청도 초당 21.2회 → 2.2회, 첫 조건 기준).
- 작업 목록 API 가 없는 예전 ComfyUI 에서는 `/queue` 를 1초 동안 나눠 쓰는 것까지만 적용된다(대기 300건 조건에서 79.9MB → 26.6MB).
- 이 수치는 조회 부하만 잰 것이다. 실제 ComfyUI 에서 영상 생성 시간이 얼마나 달라지는지는 재지 않았다.
- 다시 재려면: `.\.venv\Scripts\python.exe scripts\dev_sandbox.py --measure 20 --pending 1000 --tabs 3 --tracked 1000 --gallery --batch` (이전 판과 비교할 때는 `--source <예전 simple_ui 폴더>`, 묶음 조회 이전 화면은 `--batch` 없이).

화면 파일은 받는 쪽이 gzip 을 받으면 압축해 보낸다. 일반 화면을 여는 데 받는 양이 약 300KB(index.html 239KB + 도우미 스크립트 60KB) → 약 87KB 로 줄어든다(파일 크기 기준 계산). 이력·모델 목록 같은 글 위주의 응답도 1KB~1MB 범위에서 압축한다.

## 시험해 보고 쓰지 않기로 한 것

**SageAttention (`--use-sage-attention`)** — 커뮤니티에서 "최대 약 2배"라는 보고가 있어 실측(11/13).

| | 시드 20261113 | 시드 20261114 |
|---|---|---|
| 기본 실행 | 193.1초 | 181.6초 |
| SageAttention 켬 (`triton-windows 3.8.0.post29` + `sageattention 1.0.6`) | 202.5초 (재시작 직후, 모델 불러오기 포함) | 181.5초 |

- **빨라지지 않음.** 이유(코드): DaSiWa 워크플로가 `ModelAttentionBackend` 노드로 H3 모델의 어텐션을 이미 `comfy kitchen attention`(INT8 양자화 어텐션)으로 지정해 두었고, ComfyUI 는 이 모델별 지정을 실행 옵션보다 우선한다(`comfy/ldm/modules/attention.py` `wrap_attn` 의 `preferred_attention`). 실행 옵션은 텍스트 모델 등 나머지 부분에만 적용된다.
- 같은 시드여도 결과 영상이 달라짐(기본 실행 대비 PSNR 34dB·28.6dB). 속도 이득 없이 결과만 바뀌므로 쓰지 않음. 시험 후 두 패키지는 지웠다.

- RTX Spark: 블랙웰이라 지금 구성 그대로 동작할 것으로 봄. 128GB 에 모델이 다 올라가 RAM↔GPU 이동이 사라지는 것이 빨라지는 주 이유. 윈도우 ARM 기기라 ComfyUI·PyTorch·comfy-kitchen 의 ARM 지원 확인이 먼저 필요.
- 맥(△): ComfyUI 는 맥 GPU 에서 int8 행렬 계산을 끄고 가중치를 fp16 으로 풀어 계산하는 경로가 있음(`comfy/model_management.py` `supports_int8_compute`, `comfy/ops.py` full-precision 경로). 즉 DaSiWa int8 파일을 그대로 불러올 수는 있으나 매 스텝 풀기 때문에 느림. 텍스트 모델 nvfp4·`comfy kitchen attention`·fp16 누적 설정은 맥에서 바꿔야 할 수 있음. **맥 실측은 없음.**
